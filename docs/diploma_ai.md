# AI-подсистема интеллектуального портала работы с документами

## Введение

Данный текст подготовлен как самостоятельная часть выпускной квалификационной работы, посвященная AI-подсистеме проекта. Материал ориентирован на последующее объединение с отдельным файлом проектирования, поэтому основной акцент сделан не на постановке задачи и не на теоретическом обосновании архитектуры, а на реализованной программной структуре, выбранном технологическом стеке и фактически выполненных работах.

AI-подсистема в рассматриваемом проекте отвечает за интеллектуальную обработку документов, построение базы знаний, семантический и полнотекстовый поиск, а также генерацию ответов с использованием локальной языковой модели. По своей сути она представляет собой отдельный сервисный контур, работающий по принципу Retrieval-Augmented Generation и интегрированный в общую корпоративную систему доступа к документам.

## Назначение AI-подсистемы

Назначение AI-подсистемы состоит в том, чтобы превратить набор разрозненных документов в структурированную поисково-аналитическую базу, пригодную для диалогового взаимодействия пользователя с системой. В отличие от обычного текстового поиска, реализованная подсистема не ограничивается поиском совпадений по строкам, а поддерживает семантическое извлечение релевантных фрагментов, формирование ответа по найденному контексту и указание первоисточников.

Практически AI-подсистема решает следующие задачи:

- загрузка и индексация документов;
- извлечение текста из PDF и DOCX;
- разбиение документов на логические текстовые фрагменты;
- построение эмбеддингов для дальнейшего векторного поиска;
- хранение эмбеддингов и метаданных в PostgreSQL с расширением `pgvector`;
- выполнение гибридного retrieval по нескольким стратегиям;
- генерация ответа локальной LLM строго на основе найденного контекста;
- журналирование действий и частичная защита чувствительных данных;
- возврат источников, использованных при формировании ответа.

## Место AI-подсистемы в общей архитектуре

В составе всей системы AI-контур выделен в отдельный backend-сервис на FastAPI, который запускается независимо от пользовательского web-портала. Он взаимодействует с контейнером базы данных PostgreSQL, контейнером `Ollama`, а также с backend портала, который выступает в роли прикладного шлюза для frontend-клиента.

С точки зрения архитектуры решение построено следующим образом:

1. Администратор загружает документ в систему.
2. AI backend извлекает текст, разбивает его на чанки и строит векторные представления.
3. Чанки и эмбеддинги сохраняются в БД.
4. Пользователь отправляет вопрос.
5. AI backend извлекает релевантные чанки с помощью гибридного retrieval.
6. На основе найденного контекста локальная LLM формирует ответ.
7. Система возвращает ответ, список источников и метаинформацию для аудита.

Такое разделение позволяет независимо развивать web-контур и AI-контур, не смешивая логику пользовательского интерфейса с тяжелыми вычислительными и поисковыми операциями.

Наиболее важной таблицей является `text_chunks`, так как именно она служит основой RAG-поиска. В ней предусмотрены:

Кроме того, в SQL-схеме созданы:

- индексы для фильтрации по активности документа, году и категории.

Это означает, что система проектировалась не только на уровне логики приложения, но и на уровне оптимизации физических запросов к базе данных.

### Генерация эмбеддингов

Таким образом, ingestion-конвейер является не демонстрационной заготовкой, а полноценным рабочим механизмом пополнения базы знаний.

## Реализация гибридного retrieval

Логика извлечения релевантного контекста реализована в [backend/app/rag/retrieval.py](C:\Users\koh0\Documents\bki_system\backend\app\rag\retrieval.py). В проекте используется гибридный подход, сочетающий несколько методов поиска.

### Семантический поиск

Семантический поиск выполняется методом `similarity_search`. Алгоритм:

- строит embedding для пользовательского вопроса;
- сравнивает его с embeddings сохраненных чанков;
- использует косинусную близость;
- возвращает наиболее релевантные фрагменты.

Данный режим особенно важен в случаях, когда пользователь формулирует запрос не в тех же терминах, что и документ.

### Полнотекстовый поиск

Метод `keyword_search` использует `tsvector` и `websearch_to_tsquery('russian', ...)`. Этот механизм повышает точность поиска по ключевым словам, характерным для регламентов, правил и нормативных документов.

### Literal-поиск

Метод `literal_search` ориентирован на поиск точных вхождений терминов, названий технологий, идентификаторов и специфических выражений. Он особенно полезен в запросах, содержащих технические сущности, которые семантический поиск может трактовать слишком широко.

### Объединение результатов

После выполнения нескольких поисковых стратегий система объединяет результаты с помощью `merge_retrieved_chunks`. При этом:

- сохраняется приоритет точных совпадений;
- удаляются дубликаты;
- не теряются семантически значимые результаты.

Именно этот модуль обеспечивает баланс между точностью и полнотой извлечения контекста.

## Реализация RAG-оркестрации

Основная оркестрация RAG-сценария находится в [backend/app/rag/orchestrator.py](C:\Users\koh0\Documents\bki_system\backend\app\rag\orchestrator.py).

### Основной сценарий работы

После получения пользовательского вопроса система:

1. Выполняет retrieval релевантных чанков.
2. Формирует контекст с явными метками источников.
3. Генерирует системный и пользовательский промпты.
4. Передает данные в локальную LLM.
5. Возвращает итоговый ответ и список использованных источников.

### Работа с промптами

Промпты вынесены в [backend/app/rag/prompts.py](C:\Users\koh0\Documents\bki_system\backend\app\rag\prompts.py). В системном промпте явно зафиксировано требование:

- отвечать только на основании предоставленного контекста;
- не добавлять предположений;
- сообщать о недостаточности информации, если контекст не покрывает вопрос;
- указывать ссылки на источники.

Такая постановка промпта является важной инженерной мерой снижения галлюцинаций модели.

### Самопроверка ответа

Дополнительным достоинством реализации является встроенный этап self-correction. После генерации ответа модель получает вторичную задачу проверить, подтверждается ли ответ найденным контекстом. Если ответ не подтвержден, система возвращает сообщение о недостаточности информации.

Для прикладных корпоративных сценариев данная функция особенно важна, так как снижает риск выдачи непроверенных сведений.
