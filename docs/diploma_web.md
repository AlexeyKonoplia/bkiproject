# WEB-подсистема портала доступа к документам

## Введение

Данный текст подготовлен как самостоятельная часть выпускной квалификационной работы, посвященная WEB-подсистеме проекта. С учетом того, что в дальнейшем этот материал будет объединяться с отдельным файлом проектирования, основной акцент сделан на реализованной программной структуре, выбранном стеке технологий, архитектуре web-контуров и фактически выполненной функциональности.

WEB-подсистема в рассматриваемом проекте представляет собой прикладной пользовательский контур, обеспечивающий доступ к документной базе, чат-взаимодействие с AI-сервисом, просмотр первоисточников и административное управление загружаемыми документами. В отличие от AI-части, основной задачей данного контура является не обработка данных, а организация удобного и безопасного интерфейса взаимодействия конечного пользователя с интеллектуальной системой.

## Назначение WEB-подсистемы

WEB-подсистема предназначена для решения следующих практических задач:

- аутентификация пользователей;
- предоставление единой точки доступа к документам;
- организация интерфейса диалога с AI-моделью;
- просмотр полного содержания документов;
- переход от ответа модели к первоисточнику;
- администрирование документной базы;
- разграничение доступа между обычным пользователем и администратором.

Таким образом, web-контур выступает как пользовательская оболочка и сервисный слой поверх AI backend.

## Место WEB-подсистемы в общей архитектуре

В составе всего проекта WEB-подсистема разбита на два независимых элемента:

1. `portal_backend` — backend портала, реализующий прикладное API для frontend и проксирующий запросы к AI backend.
2. `portal_frontend` — frontend-приложение на Vue 3, реализующее визуальный интерфейс для конечного пользователя.

С архитектурной точки зрения web-контур работает следующим образом:

1. Пользователь взаимодействует с frontend через браузер.
2. Frontend обращается к backend портала.
3. Backend портала выполняет аутентификацию, получает профиль пользователя и обрабатывает прикладные сценарии.
4. Для сценариев, связанных с RAG и индексацией, backend портала обращается к основному AI backend.
5. Результат возвращается пользователю в виде страниц, списка документов, сообщений чата и источников.

Такое разделение позволяет независимо изменять пользовательский интерфейс и прикладной API, не затрагивая непосредственно AI-логику.

Выбранный стек соответствует современной практике разработки web-приложений и позволяет поддерживать четкое разделение frontend и backend-логики.

## Архитектура backend портала

Точкой входа backend портала является [portal_backend/app/main.py](C:\Users\koh0\Documents\bki_system\portal_backend\app\main.py). В приложении зарегистрированы отдельные маршруты для:

- аутентификации;
- работы с документами;
- чат-взаимодействия;
- проверки здоровья сервиса.

### Назначение backend портала

Backend портала выполняет роль промежуточного сервисного слоя. Он нужен для того, чтобы frontend:

- не обращался напрямую к AI backend;
- получал унифицированные прикладные маршруты;
- работал в рамках единой логики авторизации;
- имел отдельный слой бизнес-логики пользовательского интерфейса.

С инженерной точки зрения это удачное архитектурное решение, так как оно снижает связанность между frontend и AI-сервисом.

## Реализация аутентификации и управления доступом

### Авторизация пользователя

В [portal_backend/app/api/routes/auth.py](C:\Users\koh0\Documents\bki_system\portal_backend\app\api\routes\auth.py) реализованы:

- `/api/auth/login` для авторизации;
- `/api/auth/me` для получения профиля текущего пользователя.

На frontend соответствующая логика находится в:

- [portal_frontend/src/lib/api.js](C:\Users\koh0\Documents\bki_system\portal_frontend\src\lib\api.js);
- [portal_frontend/src/App.vue](C:\Users\koh0\Documents\bki_system\portal_frontend\src\App.vue).

Токен сохраняется в `localStorage`, а при каждом запросе автоматически подставляется в заголовок `Authorization`.

### Ролевая модель

WEB-подсистема поддерживает ролевую модель:

- `user` для обычных пользователей;
- `admin` для администраторов.

На стороне backend доступ ограничивается через зависимости безопасности, а на стороне frontend административные элементы отображаются только пользователям с соответствующей ролью.

Это обеспечивает согласованность клиентского и серверного уровней контроля доступа.

## Интеграция backend портала с AI backend

Важным элементом WEB-подсистемы является взаимодействие с AI-контуром. Для этого в [portal_backend/app/clients/app_api.py](C:\Users\koh0\Documents\bki_system\portal_backend\app\clients\app_api.py) реализован отдельный HTTP-клиент.

Через данный модуль backend портала:

- проксирует логин к основному backend;
- отправляет запросы в `/ask`;
- выполняет multipart-загрузку документов;
- обрабатывает ошибки upstream-сервиса;
- передает заголовок авторизации дальше по цепочке.

Наличие отдельного клиента делает интеграцию прозрачной и изолирует внешние вызовы от прикладных маршрутов.

## Реализация модуля работы с документами

Наиболее крупная часть backend портала реализована в [portal_backend/app/api/routes/documents.py](C:\Users\koh0\Documents\bki_system\portal_backend\app\api\routes\documents.py).

Для администратора реализованы:

- изменение статуса активности документа;

### Внутренняя логика маршрутов

Backend портала не просто отдает сырые данные из БД. В нем также реализованы:

- построение человекочитаемых сниппетов;
- подсчет количества чанков и страниц по документу;
- представление категорий в удобном формате;
- фильтрация только активных документов для пользовательского режима.

Это делает backend портала полноценным прикладным слоем, а не простым REST-оберткой над таблицами.
