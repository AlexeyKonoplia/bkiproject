# Отчет о проделанной работе по интеллектуальному сервису БКИ

## 1. Назначение разработанного интеллектуального сервиса

В рамках проекта разработан интеллектуальный сервис поддержки сотрудников Бюро кредитных историй. Его основная задача состоит в автоматизации ответов на повторяющиеся рабочие вопросы сотрудников за счет поиска информации во внутренних документах и генерации ответа на основе найденного контекста.

Сервис рассматривается именно как AI-контур системы, а не как портал доступа. В фокусе отчета находятся обработка документов, построение базы знаний, семантический и лексический поиск, генерация ответов, контроль достоверности, защита данных, аудит и тестирование. Web-портал в данном отчете учитывается только как внешний потребитель API интеллектуального сервиса и не рассматривается как самостоятельный результат разработки.

Разработанный сервис соответствует исходной постановке задачи: сотрудники БКИ получают возможность задавать вопрос на естественном языке, а система извлекает релевантные фрагменты из корпоративных документов и формирует ответ с указанием источников. При этом архитектура ориентирована на локальное развертывание внутри корпоративной инфраструктуры, что важно для соблюдения требований информационной безопасности и 152-ФЗ.

## 3. Общая архитектура интеллектуального сервиса

Интеллектуальный сервис выделен в отдельный backend-контур, расположенный в каталоге `backend`. Он реализован на FastAPI и содержит самостоятельные модули для API, работы с базой данных, загрузки документов, RAG-логики и безопасности.

Ключевые компоненты AI-сервиса:

- `backend/app/api/routes/upload.py` - прием и индексация документов;
- `backend/app/api/routes/ask.py` - обработка вопросов пользователя и возврат ответа;
- `backend/app/ingest` - извлечение текста, очистка, разбиение на чанки и построение эмбеддингов;
- `backend/app/rag` - retrieval, сбор контекста, промпты, вызов LLM и проверка ответа;
- `backend/app/db` - ORM-модели и SQL-запросы к PostgreSQL/pgvector;
- `backend/app/security` - JWT, RBAC и маскирование чувствительных данных;
- `schema/01_init.sql` - физическая схема хранения документов, чанков, эмбеддингов, событий и аудита.

Сервис развертывается в контейнерах через `docker-compose.yml`. Для AI-контура используются:

- PostgreSQL с расширением `pgvector` для хранения документов, текстовых чанков и векторных представлений;
- Ollama для локального запуска embedding-модели и генеративной языковой модели;
- AI backend на FastAPI, который связывает ingestion, retrieval, генерацию и аудит.

Такое разделение соответствует требованию on-premise развертывания: корпоративные документы, пользовательские вопросы, эмбеддинги и ответы остаются внутри внутренней инфраструктуры.

## 4. Реализованный конвейер обработки документов

Одной из центральных задач проекта была подготовка внутренней документации к интеллектуальному поиску. Для этого реализован полный ingestion-конвейер.

Сценарий обработки документа включает следующие этапы:

1. Прием файла через API.
2. Проверка поддерживаемого расширения.
3. Вычисление SHA-256 хэша для защиты от повторной индексации одного и того же файла.
4. Извлечение текста из документа.
5. Очистка текста от служебных и проблемных символов.
6. Разбиение текста на фрагменты.
7. Построение векторных представлений.
8. Сохранение исходного документа, метаданных, чанков и эмбеддингов в БД.
9. Запись события загрузки в audit log.

Сервис поддерживает форматы `PDF` и `DOCX`, что прямо соответствует заданию. Для PDF используется отдельный парсер `parser_pdf.py`, для DOCX - `parser_docx.py`. Это позволяет расширять список форматов без изменения основной RAG-логики.

Разбиение текста реализовано в `backend/app/ingest/chunking.py`. Документ обрабатывается постранично, поэтому каждый чанк сохраняет номер страницы и порядковый номер внутри страницы. Это важно не только для поиска, но и для объяснимости ответа: система может вернуть пользователю, на какой именно странице найдено основание для ответа.

Параметры чанкинга вынесены в конфигурацию:

- `CHUNK_SIZE = 1000`;
- `CHUNK_OVERLAP = 150`.

Перекрытие между чанками уменьшает риск потери смысла на границах фрагментов. Это особенно важно для регламентов и инструкций, где ответ может зависеть от соседних пунктов документа.

## 5. Построение базы знаний и хранение данных

Для хранения базы знаний реализована схема PostgreSQL с расширением `pgvector`. Основные сущности:

- `source_documents` - исходные документы и их метаданные;
- `text_chunks` - текстовые фрагменты документов;
- `ask_events` - события пользовательских вопросов;
- `feedback` - пользовательская оценка ответа;
- `audit_log` - журнал действий;
- `users`, `roles`, `user_roles` - пользователи и роли.

Наиболее важной для AI-сервиса является таблица `text_chunks`. В ней хранятся:

- текст фрагмента;
- номер страницы;
- порядковый номер чанка;
- год документа;
- категория документа;
- embedding размерности 768;
- полнотекстовый индекс `tsvector`.

В SQL-схеме созданы индексы для ускорения поиска:

- HNSW-индекс по embedding-полю для векторного поиска;
- GIN-индекс по `search_vector` для полнотекстового поиска;
- индексы по году и категории документа;
- индекс по активности документа.

Таким образом, база знаний подготовлена не только логически, но и физически: структура данных оптимизирована под гибридный поиск, фильтрацию и дальнейшее масштабирование.

## 6. Интеграция локальных AI-моделей

В проекте реализована интеграция с локальной инфраструктурой моделей через Ollama. Такой выбор соответствует требованию автономной работы внутри корпоративной ИТ-инфраструктуры и снижает риски утечки данных.

В конфигурации сервиса заданы:

- embedding-модель: `nomic-embed-text`;
- размерность embedding: `768`;
- генеративная модель: `gemma4:e4b`;
- адрес локального Ollama-сервиса: `http://ollama:11434`.

Embedding-модель используется при загрузке документов и при обработке пользовательского вопроса. На этапе загрузки она строит векторы для всех чанков. На этапе вопроса она строит вектор запроса, который затем сравнивается с векторами документов в pgvector.

Генеративная модель используется только после retrieval-этапа. Она не отвечает "из головы", а получает вопрос и найденные фрагменты документов в промпте. Это соответствует архитектуре Retrieval-Augmented Generation и снижает риск недостоверных ответов.

## 7. Реализация гибридного поиска

В задании отдельно указана необходимость семантического поиска по регламентам и базе знаний. В проекте реализован не только семантический поиск, но и гибридная retrieval-схема, объединяющая несколько стратегий.

В `backend/app/rag/retrieval.py` реализованы:

- `similarity_search` - семантический поиск по embedding-векторам;
- `keyword_search` - полнотекстовый поиск через PostgreSQL `tsvector` и `websearch_to_tsquery`;
- `literal_search` - поиск точных вхождений терминов, названий технологий, идентификаторов и специфичных выражений.

Гибридный подход выбран потому, что в корпоративных документах встречаются разные типы запросов. Для общих вопросов лучше работает семантический поиск: он способен находить смысловое совпадение даже без полного совпадения слов. Для регламентов, точных формулировок, терминов, аббревиатур и технических названий полезны keyword- и literal-поиск.

Результаты разных стратегий объединяются в `merge_retrieved_chunks`. При объединении:

- сначала учитываются точные и полнотекстовые совпадения;
- затем добавляется семантический recall;
- дубликаты чанков удаляются;
- итоговое количество фрагментов ограничивается параметром `top_k`.

Такой механизм повышает вероятность того, что в контекст генерации попадут как точные нормативные фрагменты, так и смыслово близкие части документов.

## 8. Генерация ответа на основе RAG

Основная RAG-оркестрация реализована в `backend/app/rag/orchestrator.py`.

При получении вопроса сервис выполняет следующий сценарий:

1. Принимает вопрос пользователя.
2. Выполняет гибридный retrieval.
3. Формирует список найденных чанков.
4. Создает контекст с явными метками источников вида `[source1]`, `[source2]`.
5. Формирует системный и пользовательский промпты.
6. Передает промпты локальной LLM через `ChatOllama`.
7. Получает ответ.
8. Проверяет ответ через self-correction.
9. Возвращает текст ответа, список источников и число найденных чанков.

Сервис поддерживает несколько режимов ответа:

- `brief` - краткий ответ;
- `detailed` - подробный структурированный ответ;
- `extract` - режим извлечения требований, условий, сроков и ограничений.

Наличие режимов полезно для сотрудников БКИ: один и тот же механизм может использоваться как для быстрого ответа на рабочий вопрос, так и для подробного анализа регламента.

## 9. Контроль качества и снижение галлюцинаций

В задании отдельно указана фильтрация галлюцинаций модели. В проекте реализовано несколько уровней контроля качества.

Первый уровень - системный промпт. В нем модели запрещается отвечать вне предоставленного контекста, добавлять предположения и выдумывать факты. Если информации недостаточно, модель должна сообщить о невозможности ответа на основе имеющихся данных.

Второй уровень - RAG-ограничение. Генеративная модель получает не всю базу документов, а только найденные retrieval-этапом фрагменты. Это сужает область ответа и делает результат проверяемым.

Третий уровень - self-correction. После генерации ответа запускается дополнительная проверка: модель получает вопрос, ответ и исходный контекст, после чего должна определить, подтверждается ли ответ найденными фрагментами. Если ответ признан неподтвержденным, сервис заменяет его на сообщение `Insufficient information to answer.`

Четвертый уровень - возврат источников. В ответе API возвращаются не только текст ответа, но и использованные фрагменты: `chunk_id`, `source_document_id`, имя файла, номер страницы и текст чанка. Это позволяет проверить, на каких основаниях был сформирован ответ.

## 10. Механизмы безопасности и защиты данных

Так как предметная область связана с БКИ, безопасность является одной из ключевых частей реализации.

В проекте реализованы следующие механизмы:

- JWT-аутентификация;
- ролевая модель доступа;
- роли `user` и `admin`;
- отдельные зависимости `user_required` и `admin_required`;
- аудит действий пользователей;
- маскирование чувствительных данных перед записью в журнал;
- локальное исполнение LLM и embedding-модели без обращения к внешним API.

Ролевая модель используется для разделения операций. Пользователь с ролью `user` может задавать вопросы к базе знаний. Операции загрузки и индексации документов требуют роль `admin`, так как они изменяют базу знаний и влияют на качество ответов.

В `backend/app/security/redaction.py` реализовано маскирование:

- адресов электронной почты;
- телефонных номеров;
- длинных цифровых идентификаторов;
- ФИО по эвристическим шаблонам.

Данные пользовательских запросов и операций загрузки записываются в `audit_log` уже в редактированном виде. Это снижает риск накопления чувствительной информации в технических журналах.

## 11. Аудит, обратная связь и трассируемость

Для эксплуатации интеллектуального сервиса важно понимать, какие вопросы задавались, какой моделью обрабатывались, какие источники использовались и как пользователь оценил ответ.

В проекте реализованы:

- таблица `ask_events` для фиксации факта обращения к RAG-сервису;
- таблица `audit_log` для записи действий и параметров запроса;
- таблица `feedback` для сохранения пользовательской оценки;
- `request_id` для трассировки запроса;
- маршрут `/ask/last-chunks` для восстановления последних найденных источников.

Маршрут `/ask/last-chunks` полезен для отладки и анализа качества retrieval. Он позволяет восстановить, какие именно чанки были использованы при последнем вопросе пользователя. Это важно для объяснимости AI-сервиса и последующей настройки качества поиска.

## 12. Сравнение AS-IS и TO-BE

В задании требуется провести сравнительный анализ эффективности процессов поиска информации в моделях AS-IS и TO-BE.

В проекте эта логика заложена следующим образом:

- AS-IS представлен лексическим/полнотекстовым поиском `keyword_search`;
- TO-BE представлен RAG-подходом, где используется семантический поиск по эмбеддингам и генерация ответа на основе найденного контекста;
- для оценки подготовлен скрипт `scripts/evaluate.py`;
- набор проверочных вопросов хранится в `tests/qa_set.jsonl`.

Скрипт оценки позволяет прогонять одинаковые вопросы через разные стратегии и фиксировать:

- число найденных фрагментов;
- время retrieval;
- полное время ответа;
- наличие ожидаемых подстрок в ответе;
- текст ответа при включенном вызове LLM.

Практическая разница между AS-IS и TO-BE заключается в том, что AS-IS требует от сотрудника самостоятельно искать документ, открывать найденные совпадения и интерпретировать текст. TO-BE переносит эту работу на систему: сотрудник задает вопрос на естественном языке, сервис находит релевантные фрагменты, формирует ответ и сразу показывает источники.

## 13. Тестирование интеллектуального сервиса

Для проверки AI-логики подготовлен набор автоматических тестов в каталоге `tests`.

Тестами покрыты следующие направления:

- корректность чанкинга документов;
- очистка текста от проблемных символов;
- извлечение literal-терминов;
- построение SQL-запросов для полнотекстового поиска;
- работа literal-поиска;
- объединение результатов разных retrieval-стратегий;
- дедупликация найденных чанков;
- структура промптов;
- маршрутизация вопроса с учетом истории диалога;
- маскирование чувствительных данных;
- восстановление последних найденных чанков.

Особенно важны тесты для `merge_retrieved_chunks`, потому что именно этот механизм отвечает за баланс между точными совпадениями и семантическим recall. Также важны тесты `redaction`, так как они подтверждают, что потенциально чувствительные данные не попадают в аудит в исходном виде.

## 14. Итоги выполненной работы

## 15. Вывод

Проделанная работа соответствует заданию на разработку интеллектуального сервиса. В проекте реализован не просто чат-бот, а полноценный RAG-контур: от подготовки документов и построения базы знаний до генерации ответа, контроля достоверности, аудита и оценки качества.

Главный результат заключается в том, что типовой процесс получения ответа сотрудником БКИ был переведен из ручного режима поиска и чтения документов в режим интеллектуального запроса. Вместо самостоятельного просмотра регламентов сотрудник может сформулировать вопрос, получить сгенерированный ответ и проверить его по указанным источникам. Это напрямую соответствует цели ВКР: ускорить рабочие процессы, снизить нагрузку от повторяющихся вопросов и сохранить автономность обработки данных внутри инфраструктуры БКИ.
